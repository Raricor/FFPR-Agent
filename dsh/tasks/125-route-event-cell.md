# 任务 125:`route` 走向剧情触发格时失败(「事件格，旁边没有能站的格子」)

工作目录 `dsh/`。可以改 `src/engine/skills/move.ts`、`src/engine/route/`、`test/` 下相关测试。不碰 `src/engine/stage/`、`src/engine/knowledge/`、`src/plugin/config.ts`(任务 124 同时在改),不碰 `../bridge/`、`../deploy/`、`../agent/`,不碰 git,**不连笔记本**,**不用 docker、不绕开沙箱**。

## 起因(11-11 02:47 真机，西侧山谷 577)

模型调 `route {"stops":[{"to":[13,54]},{"to":[13,33]},{"to":[13,22]}]}`。第 1 站到了;第 2 站 (13,33) 是剧情触发格「sc_e_0479_1:レナとガラフを探す（ゴブリン戦②）」,执行器连续两次失败：「(13, 33) 是事件格…,旁边没有能站的格子，没记成走不过去」,交回模型。
而上一档(11-10)同一张图上，模型用 `go` 一格一格靠近:`go [13,38]` → `go [13,34]` → `go [13,33]` 回「到达 (13, 33)」,剧情正常触发。这一档模型改成先 `go [13,38]`,剧情也触发了。所以“从远处整段走向一个剧情触发格”这条路有问题——剧情触发格本来就是要走上去的。

## 做法

1. 先查清两条路径的差别：`route` 的 move 站(`reach` 默认 cell)→ `goTo` → `navigate`,遇到目标是事件格时进了哪个分支(「旁边没有能站的格子」出自哪里),为什么从 (13,54) 出发时找不到能站的格，而从 (13,34) 出发就能直接踩上去。看 11-10 任务 83(事件格的处理)、任务 112(目标格本身不剪、实体目标格)的改动。
2. 改法：目标格是剧情触发格(Event 实体，名字以 `sc_e_`/`ev_e_` 开头或类型是触发区)时，**路线终点就是这一格本身**,走上去即可;只有“需要面向它按确认”的实体(宝箱、NPC、调查点)才走到旁边。走上去触发了剧情(状态变成 Event、出现对话)算到达，交给翻剧情的逻辑。
3. 测试：假桥插件里一条一格宽的走廊，中间一个剧情触发格：从远处 `route` 的 move 站 → 走上去、触发、算到达;`go` 同样;宝箱/NPC 仍然走到旁边。原有 move/route 测试照旧通过;`npm run check` 全过。
